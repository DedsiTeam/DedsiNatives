# Azure DevOps 无人值守编码工作项模板

本文件是 Azure DevOps 编码工作项的可复用模板。产品经理可以先按 [产研一体需求流程](../product/README.md) 在 `docs/product/` 讨论和编写本地草稿，再经人工确认通过 Azure DevOps MCP 发布。发布后 Azure DevOps 是工作项状态、验收标准和执行记录的远程事实来源；本地文件仅保留编写草稿和发布快照。

## 使用方式

采用两层工作项结构，并在编码前增加静态原型门禁：

1. **完整父需求**：描述完整业务目标、总体范围和子能力，不添加 `copilot-loop` 或 `copilot-ready`。
2. **静态原型门禁**：涉及新页面或关键交互时，产品经理先使用 VS Code 中的 Prototype Agent 在最终前端目录绘制静态页面；不调用后端，不使用 Mock 数据。
3. **编码子工作项**：描述一次 Copilot 会话、一个 worktree、一个 PR 可以独立交付的业务能力；需要原型时必须先通过原型门禁，再满足 Ready 检查后进入 Listener 队列。

小型需求如果可以一次独立实现和验收，可以直接使用编码工作项模板，不必额外创建父需求。

## 拆分判断

满足以下全部条件时，可以作为一个编码工作项：

- 只表达一个可独立验收的业务能力。
- 可以在一个分支和一个 PR 中交付。
- 所需领域规则、接口契约和验收标准已经确认。
- 前置依赖已经合并，或者本项不依赖其他未完成工作项。
- Backend 和 Frontend 可以围绕同一份最小接口契约并行实现。
- 不需要在执行过程中向人员追问关键业务决策。

出现以下任一情况时应拆分：

- 包含多个可以独立上线或验收的业务动作。
- 同时修改多个无直接一致性关系的聚合或模块。
- 预计需要多个 PR，或部分内容需要等待其他团队。
- 一部分规则已确认，另一部分仍存在领域、权限或接口歧义。
- 数据迁移、公共配置或基础设施变更可以单独形成交付门禁。

不要仅按数据库、后端、前端等技术层拆分。一个业务能力需要的后端、前端和测试可以保留在同一个编码工作项内，由 Copilot 的 Backend/Frontend 子智能体协作完成。

## 完整父需求模板

父需求用于保存整体业务目标和拆分关系，不进入 Listener 队列。

### 标题

```text
[{{业务模块}}] {{用户或角色}}可以{{完成的业务目标}}
```

### Description

```markdown
## 业务背景

{{为什么需要这项能力；当前存在什么业务问题。}}

## 目标

{{完成后用户能够获得什么结果。}}

## 已确认领域规则

- {{规则一}}
- {{规则二}}

## 总体范围

- {{包含的业务能力}}

## 排除范围

- {{本次明确不包含的能力}}

## 子工作项

- {{子工作项标题或 Azure DevOps 关联关系}}

## 依赖与顺序

- {{前置系统、工作项或发布依赖；没有时写“无”。}}

## 待决事项

- {{尚未确认的规则；没有时写“无”。}}
```

父需求存在待决事项是允许的，但相关编码子工作项在问题解决前不得添加 `copilot-ready`。

## Listener 编码工作项模板

编码工作项必须自包含。Listener 当前不会自动读取 Azure DevOps Wiki、附件、外部链接或关联工作项正文，因此不能只写“参见某文档”。所有影响本次编码的领域规则和契约都必须写入当前工作项。

### 标题

```text
[{{业务模块}}] {{一个可独立验收的业务能力}}
```

标题应描述业务结果，例如：

```text
[用户管理] 支持按名称和邮箱分页查询用户
```

避免使用纯技术标题，例如“实现用户数据库”“开发用户后端”或“制作用户页面”。

### Description

将以下内容填写到 Azure DevOps 工作项的 Description：

```markdown
## 业务目标

{{说明使用者、使用场景和期望结果。}}

## 当前上下文

- {{相关现有聚合、Endpoint、页面或流程。}}
- {{可以复用的代码、组件或接口。}}

## 已批准静态原型

- 是否需要原型：{{是/否}}
- 状态：{{NotRequired/Approved}}
- 原型工作项：{{ID；不需要时写“无”。}}
- Prototype PR：{{PR ID；不需要时写“无”。}}
- Approved Commit：{{已合并到目标分支的 Commit；不需要时写“无”。}}
- 原型 URL：{{/__prototype/WI-<id>；不需要时写“无”。}}
- 最终页面路径：{{src/react-admin/src/pages/...}}
- 最终组件路径：{{src/react-admin/src/pages/.../components；没有时写“无”。}}

### 正式研发必须保留

- {{已确认的页面布局、字段、文案和交互。}}

### 正式研发需要补全

- {{DTO、API Service、鉴权、数据状态、正式路由和菜单。}}

### 允许调整

- {{仅列出因真实契约、权限、可访问性或技术限制允许的调整。}}

## 已确认领域规则

- {{字段、状态、权限、不变量或流程规则。}}
- {{明确哪些规则不得由实现自行推断。}}

## 实现范围

- {{本工作项必须完成的业务行为。}}
- {{需要同步完成的后端、前端、迁移或测试。}}

## 排除范围

- {{明确不在本工作项中实现的内容。}}

## 接口与数据契约

### 接口

- Method：`{{GET|POST|PUT|DELETE}}`
- Path：`{{/api/...}}`
- Authentication：`{{权限或匿名规则}}`

### Request

| 字段 | 类型 | 必填 | 业务含义与约束 |
|---|---|---|---|
| `{{field}}` | `{{type}}` | {{是/否}} | {{约束}} |

### Response

| 字段 | 类型 | 可空 | 业务含义 |
|---|---|---|---|
| `{{field}}` | `{{type}}` | {{是/否}} | {{含义}} |

### 状态码与错误

- `{{status}}`：{{触发条件}}

## 依赖

- 父需求：{{Azure DevOps 父工作项 ID；没有时写“无”。}}
- 前置工作项：{{必须已经合并的工作项 ID；没有时写“无”。}}
- 外部依赖：{{服务、权限或环境依赖；没有时写“无”。}}

## 代码范围提示

- Backend：{{可能涉及的模块或路径；没有时写“无”。}}
- Frontend：{{可能涉及的模块或路径；没有时写“无”。}}
- Migration：{{是否预计需要迁移。}}

## 风险和禁止事项

- {{并发、兼容性、安全、数据迁移或不可执行操作。}}
```

接口尚未确定时，不要用猜测内容填满表格。应保留工作项未就绪，先由上游确认契约。

### Acceptance Criteria

将以下内容填写到 Azure DevOps 工作项的 Acceptance Criteria：

```markdown
## 业务验收

- [ ] {{给定前置条件时执行某操作，可以观察到明确结果。}}
- [ ] {{边界值、空数据、权限或异常场景得到明确处理。}}
- [ ] {{排除范围中的行为没有被引入。}}

## Backend 验收

- [ ] {{领域不变量、Repository/Query、Endpoint 或迁移行为。}}
- [ ] 相关后端测试通过。
- [ ] `dotnet build src/dotnet/DedsiNative.slnx` 通过。

## Frontend 验收

- [ ] 存在已批准原型时，正式实现直接复用其页面和组件，未重新生成另一套 UI。
- [ ] {{DTO、API Service、页面、路由和交互行为。}}
- [ ] 适用的 loading、empty、error、disabled、分页和重复提交状态已覆盖。
- [ ] 已删除当前工作项的原型注册项，并注册正式路由、菜单和权限。
- [ ] `bun run build` 通过。

## 集成验收

- [ ] 前后端请求和响应字段、分页、状态码及错误结构一致。
- [ ] 没有提交秘密、临时凭据、模拟数据或无关重构。
```

不涉及 Backend 或 Frontend 时删除对应部分，不保留无意义的“无需处理”检查项。

## Ready 检查

添加 `copilot-ready` 前，上游必须确认：

- [ ] 标题只描述一个业务能力。
- [ ] Description 包含本次编码所需的领域上下文，不依赖 Listener 无法读取的外部正文。
- [ ] 关键领域规则、权限和接口契约不存在待决问题。
- [ ] 涉及新页面或关键交互时，静态原型已评审通过、已合并到目标分支，并标记 `prototype-approved`。
- [ ] 原型文件位于最终生产页面目录，不含 API 调用、Mock 数据、fixture 或虚构业务记录。
- [ ] Acceptance Criteria 可由构建、测试或明确行为验证。
- [ ] 前置工作项已经合并。
- [ ] 范围和排除范围清晰。
- [ ] 工作项适合通过一个 PR 交付。

未满足 Ready 检查时，不得进入自动编码队列。

## 队列标签

需要产品静态原型时，使用以下上游标签推进评审：

```text
prototype-ready → prototype-review → prototype-approved
```

Prototype Agent 由产品经理在 VS Code 中交互使用；Listener 忽略所有 `prototype-*` 标签。原型批准并合并后，再添加编码队列标签。

普通编码工作项：

```text
copilot-loop; copilot-ready; copilot-stage-backlog; copilot-attempt-0
```

涉及 Migration、公共配置或其他高冲突文件时额外添加：

```text
copilot-exclusive
```

不要使用 `Assigned To` 把工作项分配给人员或 Agent。Listener 按 Project 和标签自动领取；上游只在首次入队时设置 `copilot-attempt-0`，之后的 `copilot-attempt-*`、`copilot-run-*`、`copilot-lease-*`、`copilot-pr` 和其他执行状态均由 Listener 维护，上游不得手工修改。
